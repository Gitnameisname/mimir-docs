# FG 5-3 보안취약점검사보고서 — 멘션 typeahead

| 항목 | 값 |
|------|----|

| 대상 | `GET /api/v1/users` + `users_repository.search_by_display_name_in_orgs` |
| 검사 영역 | R-A4 (ACL 누설) / SQL injection / Rate limit / PII / Timing |

---

## 1. R-A4 — ACL 누설 차단 (최상위)

### 1.1 위협 모델

- 공격자가 viewer 자격으로 `?q=<prefix>` 호출해 다른 organization 사용자의 display_name 누설 시도.
- Mimir 가 multi-tenant 환경 (`tenant_id` + `user_org_roles` N:M) — 한 user 가 여러 org 에 속할 수 있음.

### 1.2 방어 정합

| 층 | 방어 | 검증 |
|---|------|----|
| **모델** | `UserSearchItem` 이 `{user_id, display_name}` 만 정의 — email/role/status 자체 없음 | 회귀 `test_response_model_excludes_email_role_status`, `test_response_only_contains_user_id_and_display_name` |
| **라우터** | `viewer_user_id = actor.actor_id` — query/body 주입 차단 | 회귀 `test_viewer_user_id_must_be_keyword_only` (positional 호출 시 TypeError) |
| **Repository** | `user_org_roles` JOIN — viewer 와 같은 org 사용자만 SQL 차원에서 격리 | 회귀 `test_sql_includes_user_org_roles_join_and_viewer_self_exclude` + `test_sql_params_include_viewer_id_twice` |
| **반환 키** | `{"user_id": str(r["id"]), "display_name": r["display_name"]}` — DB 의 다른 컬럼 무시 | 회귀 `test_response_only_contains_user_id_and_display_name` |
| **본인 제외** | `WHERE u.id != %s` — 자기 자신 멘션 무의미 | SQL 검증 |
| **inactive 제외** | `WHERE u.status = 'ACTIVE'` — 비활성 사용자 노출 안 함 | SQL 검증 |

### 1.3 위반 가능 경로 분석

- ❌ **query 로 viewer_user_id 주입**: 라우터가 `q` / `limit` 만 query 로 받음. viewer_user_id 는 ActorContext 에서만.
- ❌ **다른 org 의 sysadmin 자격 우회**: 본 API 는 admin role 도 자기 org 만 — 자기 user_org_roles 안의 org 만 검색됨. SUPER_ADMIN 도 동일.
- ❌ **UNION SELECT 등 SQL injection**: psycopg2 placeholder 가 차단 (회귀 `test_wildcards_in_query_are_escaped`).
- ❌ **응답 dict 의 raw row 누설**: `_row_to_user` 안 거치고 `{user_id, display_name}` 직접 dict 구성.

### 1.4 잔여 통합 검증 (별 라운드)

- 2 organization 매트릭스 integration (org-A viewer 가 org-B 사용자 prefix 5+ 시도 → 모두 빈 결과)
- 동일 display_name 이 두 org 에 존재 → org-A viewer 는 org-A 결과만

## 2. SQL Injection

### 2.1 방어

- `psycopg2` placeholder (`%s`) 가 모든 인자 — 문자열 concat 0
- ILIKE wildcard escape: `%` `_` `\` 모두 backslash escape + `ESCAPE '\\'` 절
- query 길이 상한 (1~64자) — 라우터 Query validator

### 2.2 회귀

- `test_wildcards_in_query_are_escaped` — 악의적 `%adm` / `a_\\b` 입력이 정확히 escape 됨

### 2.3 잔여 검증 (별 라운드)

- payload 5+ 패턴 (`'; DROP TABLE users;--`, `' UNION SELECT ...`, `\\x00`, `' OR 1=1--`, `%' --`) 통합 회귀

## 3. Rate Limit (DoS / 사용자 enumeration 방어)

### 3.1 정책

- slowapi `60/minute` per user (`_USER_SEARCH_LIMIT = "60/minute"`)
- frontend `useUserSearch` 의 150ms debounce — 정상 트래픽 보호

### 3.2 enumeration 위협

- 1자 prefix 도 rate limit 적용 — alphabet 26 시도 × 60/min cap 으로 한 사용자가 1 분 내 26 prefix 시도 가능 (다른 prefix 도 포함 불가)
- multi-org user 가 자기 org 사용자 enumeration 은 의미 있지만, 본인 org 사용자는 다른 채널 (조직 내 인원 목록) 로도 알 수 있어 위험 낮음

### 3.3 잔여 (별 라운드)

- 429 응답 통합 회귀 (TestClient 로 60+ 요청 시도)

## 4. PII (제24조)

### 4.1 audit log

- `logger.info("user_search — viewer=%s, q_length=%d, result_count=%d, truncated=%s", ...)` — **q 자체 미저장**
- 회귀 자체는 정적 분석 (코드 grep) — `q_trimmed` 가 logger 호출 인자에 없음을 확인

### 4.2 응답 본문

- email / phone / 한국 주민번호 등 raw PII 부재 (응답 모델 강제)

## 5. Timing Attack

### 5.1 위협

- 같은 query 길이로 결과 0건 vs 결과 N건일 때 응답 시간 차이가 다른 org 사용자 존재 여부를 leak 할 수 있음.

### 5.2 방어 (현행)

- SQL `JOIN ... LIMIT 20` + 인덱스 (`idx_user_org_roles_user`, `idx_user_org_roles_org`) — 결과 수 무관 빠른 응답 기대
- ORDER BY display_name + id — 결정적 순서

### 5.3 잔여 정량 측정 (별 라운드)

- 1자 prefix 결과 0건 vs 결과 20건 응답 시간 측정 — 차이 < 5% 목표

## 6. 결론

본 1차 종결 시점 6 보안 영역 중 5 영역 회귀 통과 (R-A4 / SQL injection / PII / Rate limit / 응답 모델). Timing 정량 측정과 통합 회귀 (TestClient + 2 organization 매트릭스) 는 별 라운드.
