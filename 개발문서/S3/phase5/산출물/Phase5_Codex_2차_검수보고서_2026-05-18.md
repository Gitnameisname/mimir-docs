## 1. 결론

1차 검수에서 지적된 주요 항목 일부는 코드상 보완이 들어왔으나, **문서가 선언한 "통합 패치 후 PASS" 상태는 현재 작업공간에서 재현되지 않는다.** 특히 frontend test gate가 TypeScript 설정에서 즉시 실패하고, backend user search 통합 테스트는 문서 설명과 달리 DB 의존성을 override하지 않아 실제 DB 접속을 시도한다.

또한 `NodeRenderer`의 read-only mark 렌더링은 helper 인덱싱 테스트만 통과 가능한 구조이며, 실제 section 하위 재귀 렌더링에서는 `contentSnapshot`이 끊겨 annotation mark가 렌더되지 않는 경로가 남아 있다. 따라서 "Codex P1 4건 + 독립검수 §3 5건 닫힘"이라는 회고 문구는 정정되어야 한다.

## 2. 주요 발견

### [P1] F-01. Frontend 회귀 게이트가 현재 환경에서 시작 전 실패한다

- 근거:
  - `frontend/tsconfig.test.json:5` — `"moduleResolution": "node"`
  - 실행 결과: `npm run test`가 `TS5107: Option 'moduleResolution=node10' is deprecated and will stop functioning in TypeScript 7.0` 에서 종료
  - `Phase5_1라운드_종결회고.md:64-70`, `:96-101` — frontend `npm run test` PASS / node:test baseline 유지 / tsc 0 error 주장

영향:

- 신규 `NodeRendererMarkFg52`, `MentionDetectFg53` 테스트뿐 아니라 전체 frontend test suite가 실행 단계까지 가지 못한다.
- 회고의 "운영자 실측 확인"은 현재 작업공간 기준으로 재현 불가다.

권고:

- `tsconfig.test.json`에 TypeScript 6 기준 설정을 반영하거나 `ignoreDeprecations`를 명시하고, 그 후 전체 `npm run test` 결과로 회고 수치를 갱신한다.

### [P1] F-02. users_search 통합 테스트가 DB override 없이 실제 DB 접속을 시도한다

- 근거:
  - `backend/tests/integration/test_user_search_fg53_integration.py:6-8` — TestClient + dependency_overrides로 인증과 DB 의존성을 합성한다고 문서화
  - `backend/tests/integration/test_user_search_fg53_integration.py:48-67` — 실제 `_make_client`는 `resolve_current_actor`와 `_users_repository`만 교체하고 DB dependency는 교체하지 않음
  - `backend/app/api/v1/users_search.py:33`, `:86` — 라우터는 모듈에 import된 `get_db()`를 직접 호출
  - 실행 결과: `psycopg2.OperationalError: connection to server at "192.168.0.31", port 5432 failed: Operation not permitted`
  - `Phase5_1라운드_종결회고.md:67-70`, `:125` — integration PASS 주장

영향:

- 통합 테스트는 in-process mock 통합이 아니라 외부 DB 환경 의존 테스트다.
- sandbox/CI에서 재현 가능성이 낮고, R-A4 query 주입 차단·response model·trace metadata 회귀가 실제로 녹색인지 확인되지 않았다.

권고:

- `users_search_module.get_db`를 테스트에서 contextmanager mock으로 교체하거나 FastAPI dependency로 주입 가능하게 리팩터링한다.
- 그 후 `test_user_search_fg53_integration.py`를 단독 실행해 18건 PASS를 재기록한다.

### [P1] F-04. NodeRenderer section 하위에서는 mark-aware 렌더링이 끊긴다

- 근거:
  - `frontend/src/features/documents/NodeRenderer.tsx:100-103` — `contentSnapshot`으로 `inlineByNodeId` 인덱스 생성
  - `frontend/src/features/documents/NodeRenderer.tsx:165-172` — section child 렌더링 재귀에서 `contentSnapshot={null}` 전달
  - `frontend/tests/NodeRendererMarkFg52.test.tsx:68-87` — 중첩 인덱싱 helper만 검증하고, 실제 `NodeRenderer` 재귀 렌더링은 검증하지 않음
  - `Phase5_1라운드_독립검수보고서.md:253` — DetailPage `NodeRenderer` mark 인식으로 본문→Panel 경로가 닫혔다고 주장

영향:

- 일반적인 문서 구조가 `section -> paragraph/heading`이면 하위 node의 annotation/hashtag/wikilink mark가 상세 페이지에서 plain text fallback으로 렌더된다.
- AnnotationMark click → panel highlight 경로도 section 하위 본문에서는 동작하지 않는다.

권고:

- 재귀 호출에 `contentSnapshot` 또는 이미 계산된 `inlineByNodeId`를 유지 전달한다.
- helper 테스트가 아니라 실제 렌더 결과에 `.annotation-mark[data-annotation-id]`가 존재하는지 확인하는 회귀를 추가한다.

### [P2] F-05. save_draft sanitize가 annotation 로딩 전 실행되면 유효 mark까지 제거할 수 있다

- 근거:
  - `frontend/src/features/documents/hooks/useDocumentAnnotations.ts:33-35`, `:47-50` — query data가 없으면 annotations는 `[]`, validIds는 빈 Set
  - `frontend/src/features/editor/DocumentEditPage.tsx:73-80` — validIds를 ref에 저장하되 loading 상태와 구분하지 않음
  - `frontend/src/features/editor/DocumentEditPage.tsx:171-180` — save 시 항상 `cleanInvalidAnnotationMarks(doc, validAnnotationIdsRef.current)` 호출
  - `frontend/src/features/editor/DocumentEditPage.tsx:209-214` — 명시 저장은 annotation query 완료 여부를 확인하지 않음

영향:

- 편집 페이지 진입 직후 annotation list가 아직 로딩 중인데 사용자가 저장하거나 자동 저장 타이밍이 맞으면, 빈 validIds 기준으로 본문 내 annotation marks가 모두 stale로 판단될 수 있다.
- 이는 "stale id 제거" 목적을 넘어 정상 mark 손실로 이어질 수 있다.

권고:

- annotation query가 성공적으로 로드되기 전에는 sanitize를 건너뛰거나, `validIds`와 `isLoaded`를 분리해 저장 조건에 반영한다.
- "삭제된 annotation만 제거" 케이스와 "annotation query loading 중 저장" 케이스를 별도 회귀로 추가한다.
