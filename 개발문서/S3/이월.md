## 2. Phase 6 (운영 안전) 이월 항목

`Phase6_공식종결보고서.md` §7 의 7항. 2026-05-18 공식 종결 시점 등록.

### O1. per-user rate-limit keying

- **현재**: slowapi `_get_client_ip` 기반 per-IP.
- **목표**: per-user (또는 per-actor) keying — NAT/공유 IP 환경의 false-positive 차단.
- **분류**: **Phase 7 흡수 검토** — FG 7-4 (cluster-wide rate-limit) 의 자연 확장.
- **의존**: Valkey 도입 (FG 7-1) 후가 자연스러움. in-process limiter 만으론 per-actor key 가 의미 약함.
- **승인**: P1 (rate-limit 정책 변경).
- **출처**: `phase6/Phase 6 개발계획서.md` §6.1, `phase6/산출물/FG6-1_검수보고서.md` §5.

### O2. archive 자체의 sub-retention (1년 cold storage / 2년 PURGE)

- **현재**: `audit_events_archive` / `annotations_archive` 가 무기한 보존.
- **목표**: archive 행수 폭증 방지 — 1년 후 cold storage (예: S3 / Glacier) 이동, 2년 후 PURGE.
- **분류**: **별 라운드** — 인프라 (cold storage backend) 결정 후 진행.
- **의존**: 운영 인프라 측 cold storage 가용성 (사내 S3 호환 / Glacier 등).
- **승인**: P1 (데이터 폐기 정책).
- **출처**: `phase6/Phase 6 개발계획서.md` §7 R-05, `phase6/산출물/FG6-2_보안취약점검사보고서.md` §3 R1.

### O3. annotation 외 텍스트 필드 sanitize 일괄 적용

- **현재**: `app.utils.content_sanitizer` 가 annotation content / mention snippet 에만 적용.
- **목표**: workflow comment / tag description / draft note 등 다른 사용자 텍스트 필드도 동일 utility 적용.
- **분류**: **별 라운드** — 코드 변경은 작지만 영향 범위 (회귀) 가 넓음. 별 라운드에서 일괄 적용 + 회귀.
- **의존**: 없음.
- **승인**: standard (보안 강화 — 사용자 텍스트 입력 검증).
- **출처**: `phase6/산출물/FG6-3_보안취약점검사보고서.md` §3 R1.

### O4. admin 14 endpoint × 4 시나리오 전수 route-level 회귀

- **현재**: helper 단위 8건 + 대표 route-level 5건 (4 endpoint group 전부 cover) + 코드 점검표 3축.
- **목표**: 14 endpoint × {본인-org / 다른-org / SUPER-본인 / SUPER-횡단} 4 시나리오 = 56건 route-level.
- **분류**: **별 라운드** — 운영자 요구 시. helper 단일 진입점 구조에서 추가 가치 제한적.
- **의존**: 없음.
- **승인**: standard (회귀 보강).
- **출처**: `phase6/산출물/FG6-4_Admin엔드포인트_점검표.md` §3, `phase6/산출물/Phase6_Codex_4차_검수보고서.md` §6.

### O5. SUPER_ADMIN 횡단 빈도 알람

- **현재**: `admin.cross_org_access` event_type 으로 audit_events 에 emit 만 함. 알람 없음.
- **목표**: 일/주 단위 빈도 임계 초과 시 운영자 알람 (예: 1일 10회 초과). 또는 같은 SUPER_ADMIN 의 cross-org 빈도가 평소의 10× 초과 시 즉시 알람.
- **분류**: **Phase 7 흡수 검토** — Phase 7 의 observability 라운드 (별 산출물) 또는 별 모니터링 dashboard.
- **의존**: Phase 7 observability 인프라.
- **승인**: standard (alert 정책 — `alert_rules` 테이블 활용).
- **출처**: `phase6/산출물/FG6-4_Admin엔드포인트_점검표.md` §4, `phase6/공식종결보고서.md` §7.

### O6. 다중 org admin 의 list UX

- **현재**: non-SUPER_ADMIN 의 admin list endpoint (`scope-profiles` / `agents`) 가 organization_id 미지정 시 본인 첫 org 으로 강제.
- **문제**: 한 사용자가 여러 organization 의 ORG_ADMIN 인 경우 첫 org 외 자원은 명시적으로 organization_id query 지정해야 함.
- **목표**: 다중 org admin UX 결정 — (a) 전체 union, (b) org 선택 dropdown, (c) 현재 방식 유지.
- **분류**: **별 ADR** — 정책 결정 (Privacy / 사용성 / 보안 trade-off).
- **의존**: 운영자 합의.
- **승인**: P1 (UX 정책).
- **출처**: `phase6/Phase 6 개발계획서.md` §6.2, `phase6/산출물/FG6-4_Admin엔드포인트_점검표.md` §3, `phase6/공식종결보고서.md` §7.

### O7. `audit_emitter.emit` 실패 시 P1 위반 처리 정책

- **현재**: `ensure_actor_can_access_org` 의 SUPER_ADMIN cross-org audit emit 실패 시 warning 로그 후 통과 (가용성 우선).
- **목표**: emit 실패를 P1 위반으로 보고 거부할지 (감사 의무 강화), 또는 현 정책 유지할지 결정.
- **분류**: **운영자 결정** — 감사 의무 강도는 정책 사안. 결정 후 별 라운드에서 코드 시정.
- **의존**: 운영자 합의 + 감사 인프라 가용성 (audit 실패 빈도 실측).
- **승인**: P1 (보안 정책).
- **출처**: `phase6/산출물/Phase6_Codex2차_시정보고서.md` §6.2, `phase6/공식종결보고서.md` §7.
